01Visão Geral do Produto

Finance Pro é um aplicativo de acompanhamento de carteira de observação (watchlist) de ativos financeiros — ações, ETFs e criptomoedas — com cotações, séries históricas, notícias agregadas e um assistente conversacional.

1.1 Funcionalidades

1.2 Plataformas suportadas

O projeto mantém runners nativos para Android (com.example.easy_finance), iOS (deployment target 13.0), Web, Windows, macOS e Linux. O foco de produto e de validação de UX é mobile; os demais alvos são funcionais por consequência do toolkit, e não receberam ajuste específico de layout responsivo.

1.3 Premissas do domínio

  • Todos os preços são expressos e formatados em dólar norte-americano (price_usd, NumberFormat.simpleCurrency(locale: 'en_US')).
  • A direção do movimento do ativo é fornecida pelo backend como string de domínio em português ("subindo" / demais valores) e não é derivada no cliente a partir da série histórica.
  • Tickers seguem a nomenclatura do provedor de mercado a montante (ex.: AAPL, BTC-USD), sem normalização no cliente.

A supressão é declarada no nível do projeto, e não por // ignore: espalhado nos arquivos, mantendo os arquivos-fonte livres de ruído. Essa escolha tem o custo de também silenciar eventuais ocorrências legítimas em código autoral.

3.2 Regra de dependência

As dependências apontam sempre para dentro. A camada de apresentação conhece apenas as abstrações declaradas em lib/domain/repositories/; nenhuma view ou view model importa package:dio. A resolução da implementação concreta ocorre em tempo de execução, através dos providers declarados junto de cada implementação:

// lib/data/repositories/asset_repository_impl.dart
final assetRepositoryProvider = Provider<AssetRepository>((ref) =>
    AssetRepositoryImpl(ref.read(dioClientProvider)));

O tipo exposto pelo provider é a abstração (Provider<AssetRepository>), não a implementação. Isso permite substituir a implementação em testes por overrideWithValue sem qualquer alteração no código de produção.

Desvio consciente do modelo canônico Os modelos de dados residem em lib/data/models/ e são referenciados diretamente pelas interfaces do domínio, em vez de existirem entidades de domínio separadas com mapeadores. A duplicação model↔entity foi considerada desproporcional para um cliente cujo modelo de leitura espelha o contrato da API. O custo dessa escolha é que uma mudança de schema no backend propaga até a camada de apresentação sem barreira intermediária.

3.3 Fluxo de uma requisição

Exemplo completo — carregamento da tela inicial:

HomeView.build() │ ├─ ref.watch(homeNotifierProvider) ────────► reconstrói ao mudar HomeState │ └─ HomeNotifier() [construtor] → load() │ ├─ watchlistRepo.getWatchlist() ──► GET /profile/watchlist ├─ _applyOrder(...) ──► SharedPreferences['watchlist_order'] │ ├─ Future.wait( getQuote(t) ∀t )──► GET /assets/{ticker} [paralelo] ├─ Future.wait( getHistory(t) ∀t )──► GET /assets/{ticker}/history [paralelo] │ ├─ state = state.copyWith(quotes, history, loading: false) │ └─ _loadNews(tickers) [não aguardado] └─ Future.wait( getNews(t) ∀t )─► GET /assets/{ticker}/news └─ state = state.copyWith(news, newsLoading: false)

Duas características do fluxo merecem destaque. Primeiro, as chamadas por ticker são disparadas em paralelo via Future.wait, de modo que a latência total tende ao maior tempo individual, e não à soma. Segundo, o carregamento de notícias é deliberadamente não aguardado: a tela renderiza cotações e gráficos assim que disponíveis, e a faixa de notícias preenche-se em seguida, com skeleton próprio.

4.1 Convenções estruturais

  • Agrupamento por feature dentro da camada. Cada tela possui um diretório próprio sob views/, com um subdiretório widgets/ para componentes que só ela utiliza. Componentes usados por mais de uma feature sobem para core/widgets/.
  • Provider colocado junto do que ele constrói. Não há arquivo central de injection; cada provider é declarado no final do arquivo do serviço ou repositório correspondente. Isso mantém a definição próxima do consumidor e evita um ponto único de acoplamento.
  • Espelhamento na árvore de testes. test/ reproduz a hierarquia de lib/, tornando previsível a localização do teste de qualquer unidade.

05Camada de Domínio

A camada de domínio contém exclusivamente contratos. São quatro interfaces abstratas, sem dependência de Flutter, Dio ou qualquer detalhe de infraestrutura.

5.1 Contratos

abstract class AuthRepository {
  Future<AuthTokenModel> login(String email, String password);
  Future<UserModel> register({
    required String name,      required String email,
    required String password,  required String birthDate,
    required String investorProfile,
  });
}

abstract class AssetRepository {
  Future<List<AssetModel>>        search(String query);
  Future<AssetQuoteModel>         getQuote(String ticker);
  Future<List<HistoryPointModel>> getHistory(String ticker, String period);
  Future<List<NewsItemModel>>     getNews(String ticker);
  Future<List<DividendModel>>     getDividends(String ticker);
  Future<FinancialsModel>         getFinancials(String ticker);
}

abstract class WatchlistRepository {
  Future<List<AssetModel>> getWatchlist();
  Future<void> addAssets(List<AssetModel> assets);
  Future<void> removeAssets(List<String> tickers);
}

abstract class ChatRepository {
  Future<String> sendMessage(String userMessage);
}

5.2 Propriedades de projeto

PropriedadeConsequência prática
Ausência de camada de use caseA orquestração reside nos view models. Para o volume atual de regras — combinação de chamadas e transformação de listas — uma classe por caso de uso adicionaria indireção sem isolar comportamento novo. Se surgirem regras compartilhadas entre telas, esse é o ponto natural de extração.
Erros propagados como exceçõesNão há tipo Result/Either. As implementações deixam DioException propagar, e cada view model converte a exceção em estado de erro no seu catch. A abordagem é mais leve, ao custo de a assinatura do método não declarar as falhas possíveis.
Granularidade fina do AssetRepositoryMétodos separados por recurso (getQuote, getHistory, getNews…) permitem que o chamador componha exatamente as chamadas necessárias e paralelize à vontade — usado intensivamente em HomeNotifier.load().
ChatRepository minimalistaUma única operação sendMessage, sem histórico de conversa no contrato. A troca do dublê local por um serviço real de IA exige apenas uma nova implementação e a alteração de uma linha no provider.
Métodos não consumidos getDividends e getFinancials estão declarados, implementados e cobertos pelo contrato, mas nenhuma tela os consome no estado atual. Correspondem a uma tela de detalhe de ativo prevista e ainda não construída. São dívida deliberada, não código morto acidental.

Mapeamento de nomenclatura

O backend expõe campos em snake_case; o código Dart usa lowerCamelCase. A tradução é declarada campo a campo com @JsonKey, em vez de uma estratégia global de conversão de nomes:

@freezed
class AssetQuoteModel with _$AssetQuoteModel {
  const factory AssetQuoteModel({
    required String ticker,
    required String name,
    @JsonKey(name: 'icon_url')  required String iconUrl,
    @JsonKey(name: 'price_usd') required double priceUsd,
    required String direction,
  }) = _AssetQuoteModel;

  factory AssetQuoteModel.fromJson(Map<String, dynamic> json) =>
      _$AssetQuoteModelFromJson(json);
}

A anotação explícita é mais verbosa, porém torna o contrato auditável na leitura do próprio modelo e resiste a campos que fujam do padrão.

Obrigatoriedade dos campos

FinancialsModel declara todos os campos como anuláveis, refletindo que indicadores fundamentalistas são indisponíveis para diversas classes de ativo — criptomoedas não possuem P/E nem dividend yield. Os demais modelos usam required, o que faz a desserialização falhar de forma explícita e imediata diante de uma resposta incompleta, em vez de propagar null silenciosamente até a UI.

6.2 Fontes de dados

Cliente HTTP

final dioClientProvider = Provider<Dio>((ref) {
  final dio = Dio(BaseOptions(
    baseUrl: ApiConstants.baseUrl,
    connectTimeout: const Duration(seconds: 15),
    receiveTimeout: const Duration(seconds: 30),
    headers: {'Content-Type': 'application/json'},
  ));
  final storage = ref.read(secureStorageServiceProvider);
  final onLogout = ref.read(logoutCallbackProvider);
  dio.interceptors.add(AuthInterceptor(storage, onLogout: onLogout));
  return dio;
});

Os timeouts são assimétricos por intenção: 15 s para estabelecer conexão e 30 s para receber a resposta, acomodando endpoints de série histórica com período max, cuja carga útil é substancialmente maior.

Catálogo de rotas

ApiEndpoints centraliza todos os caminhos como constantes ou funções puras. Nenhuma URL aparece literal em repositório ou view model, de modo que uma alteração de rota no backend tem ponto único de manutenção — e é diretamente testável, como comprovam os 13 casos de api_endpoints_test.dart.

6.3 Implementações de repositório

As implementações são deliberadamente finas: montam a requisição, desserializam a resposta e retornam. Não realizam cache, retry, log nem tratamento de erro — responsabilidades atribuídas ao interceptador (autenticação) e aos view models (apresentação do erro).

@override
Future<List<HistoryPointModel>> getHistory(String ticker, String period) async {
  final r = await _dio.get(
    ApiEndpoints.assetHistory(ticker),
    queryParameters: {'period': period},
  );
  return (r.data as List)
      .map((e) => HistoryPointModel.fromJson(e as Map<String, dynamic>))
      .toList();
}

Sincronização diferencial da watchlist

WatchlistRepository expõe operações em lote (addAssets, removeAssets) em vez de operações unitárias. O ProfileNotifier mantém a lista original e a lista selecionada em memória, calcula a diferença no momento de salvar e emite no máximo duas requisições — evitando uma chamada de rede por toque do usuário:

final toAdd = state.selectedAssets
    .where((a) => !originalTickers.contains(a.ticker)).toList();
final toRemove = state.originalWatchlist
    .where((a) => !selectedTickers.contains(a.ticker))
    .map((a) => a.ticker).toList();

if (toAdd.isNotEmpty)    await watchlistRepo.addAssets(toAdd);
if (toRemove.isNotEmpty) await watchlistRepo.removeAssets(toRemove);

Repositório de chat

MockChatRepository implementa o contrato com um dicionário de palavras-chave (preço, tendência, dividendo, crypto, etf, perfil, watchlist, ação, recomendação) mapeadas a respostas em Markdown, com variantes sorteadas e latência artificial entre 800 ms e 1.500 ms para simular processamento. Existe uma resposta genérica para entradas não reconhecidas. O objetivo é permitir o desenvolvimento e a validação completa da UI de conversa antes da disponibilidade do serviço de IA.

07Camada de Apresentação

A apresentação segue MVVM: cada tela relevante possui um view model (StateNotifier) que expõe um estado imutável, e as views são funções desse estado.

7.1 Padrão de estado

Todo view model expõe uma única classe de estado imutável, com valores-padrão no construtor e copyWith. Estados de carregamento, erro e dados coexistem no mesmo objeto, o que elimina combinações inconsistentes entre variáveis independentes:

class HomeState {
  final bool loading;
  final bool refreshing;
  final String? error;
  final List<AssetQuoteModel> quotes;
  final String selectedPeriod;
  final Map<String, List<HistoryPointModel>> history;
  final List<NewsItemModel> news;
  final bool newsLoading;

  const HomeState({ this.loading = true, this.refreshing = false, ... });
  HomeState copyWith({ ... });
}
Distinção entre loading e refreshing A primeira carga exibe skeleton em tela cheia; o pull-to-refresh mantém o conteúdo atual visível e mostra apenas um indicador discreto no cabeçalho. Sem os dois sinalizadores separados, atualizar a tela faria o conteúdo desaparecer e reaparecer — regressão perceptível de qualidade.

Nota de implementação: em todos os copyWith do projeto, o campo error é atribuído diretamente (error: error) e não com o operador ??. É intencional: permite limpar o erro em uma transição de estado bem-sucedida. A contrapartida é que qualquer copyWith que não repasse o erro o descarta — comportamento que precisa ser conhecido por quem edita esses métodos.

7.3 Decisões de UX com impacto técnico

Ordem manual da watchlistReorderableListView na Home; a nova ordem de tickers é gravada em SharedPreferences e reaplicada em _applyOrder a cada carga. Ativos ausentes da ordem salva são anexados ao final, o que mantém o comportamento correto quando a watchlist muda no servidor.

8.2 Convenções de acesso

A distinção entre ref.watch e ref.read é aplicada de forma consistente:

  • ref.watch — exclusivamente em build, para estabelecer a assinatura reativa que reconstrói o widget.
  • ref.read — em callbacks, construtores e métodos, onde a reconstrução não é desejada.

Dentro dos view models, os repositórios são obtidos por _ref.read(...) no momento do uso, e não capturados no construtor. Isso permite que uma sobrescrita de provider feita em teste seja observada mesmo após a construção do notifier.

8.3 Ciclo de vida

HomeNotifier e ProfileNotifier disparam a carga inicial no próprio construtor. A consequência é que a primeira leitura do provider já inicia o tráfego de rede, sem necessidade de initState na view — e o estado é preservado enquanto o provider permanecer vivo, evitando recarga a cada troca de aba.

8.4 Testabilidade

A sobrescrita de providers é o mecanismo central de teste da camada de apresentação:

final container = ProviderContainer(
  overrides: [
    watchlistRepositoryProvider.overrideWithValue(mockWatchlist),
    assetRepositoryProvider.overrideWithValue(mockAsset),
  ],
);
addTearDown(container.dispose);

Nenhum singleton global, service locator ou estado estático precisa ser reinicializado entre testes, o que elimina uma classe inteira de falhas intermitentes por vazamento de estado.

Adoção parcial da API moderna O projeto utiliza StateNotifier, e não a API mais recente Notifier/AsyncNotifier, ainda que riverpod_generator conste nas dependências de desenvolvimento. A escolha é coerente internamente — não há mistura de padrões — mas representa dívida técnica frente à direção do ecossistema Riverpod. A migração é mecânica e pode ser feita por notifier, sem alteração das views.

As quatro abas são declaradas como StatefulShellRoute.indexedStack, com um StatefulShellBranch por aba.     StatefulShellBranch(routes: [GoRoute(path: '/profile', ...)]),
    StatefulShellBranch(routes: [GoRoute(path: '/chat',    ...)]),

Em AppShell._onTap, o parâmetro initialLocation: index == shell.currentIndex implementa o comportamento esperado de barra de abas: tocar na aba já ativa retorna à raiz daquele ramo, enquanto tocar em outra aba preserva onde o usuário estava.

9.3 Guarda de rota

redirect: (context, state) async {
  final storage = ref.read(secureStorageServiceProvider);
  final hasToken = await storage.hasToken();
  final loc = state.uri.toString();
  final publicRoutes = ['/', '/login', '/register'];

  if (!hasToken && !publicRoutes.contains(loc)) return '/login';
  if (hasToken && (loc == '/login' || loc == '/register')) return '/home';
  return null;
}

A guarda é bidirecional: além de bloquear rotas protegidas sem sessão, impede que um usuário autenticado retorne às telas de login e cadastro. Sendo assíncrona, consulta o armazenamento seguro a cada navegação, o que garante decisão sempre baseada no estado real de credencial — e não em cópia em memória potencialmente desatualizada por um 401 tratado pelo interceptador.

Custo e mitigação Ler o Keychain/EncryptedSharedPreferences a cada navegação implica uma operação de I/O por transição. Para o volume de rotas deste aplicativo o impacto é imperceptível. Caso o número de rotas cresça, o caminho natural é manter um StateProvider<bool> de sessão em memória, sincronizado pelo interceptador e pelo fluxo de login, e usar refreshListenable.

10Autenticação e Segurança

10.1 Fluxo de autenticação

Cadastro Login ──────── ───── RegisterView LoginView │ AuthNotifier.register() │ AuthNotifier.login() ▼ ▼ POST /user/register POST /auth/login (application/json) (x-www-form-urlencoded, │ grant_type=password) ▼ │ UserModel ▼ │ AuthTokenModel {access_token, token_type} └──── auto-login ─────────────► │ ▼ SecureStorage.saveToken(access_token) │ ▼ state = AuthState(success) → context.go('/home') Requisições subsequentes Expiração / revogação ──────────────────────── ───────────────────── AuthInterceptor.onRequest AuthInterceptor.onError └─ Authorization: Bearer <token> └─ if (status == 401) ├─ clearToken() └─ onLogout()

10.2 Formato da requisição de login

O endpoint de login segue o padrão OAuth2 Resource Owner Password Credentials, exigindo application/x-www-form-urlencoded com os campos username, password e grant_type — convenção adotada por FastAPI com OAuth2PasswordRequestForm. O corpo é montado com Uri.encodeComponent em cada valor, prevenindo quebra do formato por caracteres reservados presentes em e-mails ou senhas:

data: 'username=${Uri.encodeComponent(email)}'
      '&password=${Uri.encodeComponent(password)}'
      '&grant_type=password',
options: Options(contentType: 'application/x-www-form-urlencoded'),

10.4 Tratamento centralizado de sessão expirada

AuthInterceptor concentra duas responsabilidades transversais, mantendo repositórios e view models livres de lógica de autenticação:

  • onRequest — lê o token e, se presente, injeta o cabeçalho Authorization: Bearer <token>. Nenhum repositório manipula cabeçalhos de autenticação.
  • onError — ao detectar HTTP 401, limpa o token armazenado e invoca onLogout. Como a guarda de rota consulta o armazenamento a cada navegação, a próxima transição já redireciona para /login.

12.2 Serialização do usuário

UserStorageService grava o JSON já em snake_case, o mesmo formato retornado pela API. A leitura pode assim reaproveitar UserModel.fromJson sem transformação intermediária, e um payload gravado por versão anterior permanece compatível.

A leitura é defensiva: uma falha de parse retorna null em vez de propagar exceção.

Future<UserModel?> readUser() async {
  final raw = await _storage.read(key: _userKey);
  if (raw == null) return null;
  try {
    return UserModel.fromJson(jsonDecode(raw) as Map<String, dynamic>);
  } catch (_) {
    return null;   // dado corrompido ou de schema antigo → trata como ausente
  }
}

O efeito prático é que uma mudança de schema entre versões do aplicativo degrada para “usuário não encontrado localmente” em vez de travar a tela de perfil.

12.3 Reconciliação da ordem da watchlist

A ordem persistida é uma lista de tickers, não de objetos completos. Em _applyOrder, os ativos vindos do servidor são indexados por ticker e reordenados conforme a lista salva; ativos ausentes da ordem — adicionados em outro dispositivo, por exemplo — são anexados ao final:

final map = {for (final a in assets) a.ticker: a};
final ordered   = order.where(map.containsKey).map((t) => map[t]!).toList();
final remaining = assets.where((a) => !order.contains(a.ticker)).toList();
return [...ordered, ...remaining];

O algoritmo é tolerante à divergência em ambas as direções: tickers salvos que já não existem são descartados, e tickers novos aparecem sem exigir invalidação da preferência.

Ausência de cache de dados de mercado Cotações, históricos e notícias não são persistidos; toda abertura da tela inicial busca dados frescos. Para dados de mercado essa é a escolha correta — informação de preço desatualizada é pior do que ausência de informação. O único conteúdo remoto cacheado são os ícones de ativos, via cached_network_image, por serem imutáveis na prática.

14.1 Configuração

O projeto utiliza o pipeline oficial flutter gen-l10n, habilitado por generate: true em pubspec.yaml. São dois locales — pt (padrão) e en — com 38 chaves traduzidas. O arquivo-modelo é o inglês, convenção que facilita a inclusão de novos idiomas a partir de uma base neutra.

14.2 Delegates e seleção de idioma

MaterialApp.router registra GlobalMaterialLocalizations, GlobalWidgetsLocalizations e GlobalCupertinoLocalizations, o que traduz também os componentes nativos do framework — rótulos de diálogo, seletor de data e menus de contexto.

A seleção é explícita e persistida: LocaleNotifier lê locale_code de SharedPreferences na construção e grava a cada troca. O idioma não segue o locale do dispositivo por padrão, decisão que privilegia previsibilidade — a escolha do usuário prevalece entre sessões.

14.3 Cobertura e limitação atual

Internacionalização parcial A infraestrutura de i18n está completa e funcional, mas parte das strings permanece embutida em português diretamente nos widgets — rótulos da barra de navegação (“Início”, “Perfil”, “IA Chat”, “Config”), títulos de seção da Home (“Watchlist”, “Gráficos”, “Notícias”), mensagens de erro dos view models e as respostas do assistente. Com o idioma em EN-US, essas partes seguem exibindo texto em português. A correção é mecânica — mover cada literal para os arquivos .arb e substituir por AppLocalizations.of(context) — mas ainda não foi concluída.

As mensagens de erro representam um caso à parte: por estarem nos view models, que não possuem BuildContext, a externalização exige uma decisão adicional de projeto — retornar chaves de erro em vez de texto pronto, deixando a tradução para a camada de view.

16Registro de Decisões Técnicas

Consolidação das decisões estruturais, com alternativas consideradas e o custo assumido em cada caso.

#DecisãoMotivaçãoAlternativa preterida e custo assumido
01Clean Architecture em 3 camadas Isola a UI dos detalhes de transporte e permite substituir implementações sem tocar na apresentação — condição para testar view models sem rede. Arquitetura em camada única. Rejeitada: acoplaria as telas ao Dio e inviabilizaria os testes de view model.
02Modelos de dados compartilhados com o domínio O modelo de leitura do cliente espelha o contrato da API; entidades separadas com mapeadores dobrariam o código sem isolar comportamento. Entidades de domínio + mappers. Custo assumido: mudanças de schema no backend propagam até a apresentação.
03Riverpod como DI e estado Resolução segura em tempo de compilação, sobrescrita trivial em testes, sem singleton global. Provider + GetIt. Rejeitada: dois mecanismos para um problema, com registro global mutável.
04StateNotifier em vez de AsyncNotifier Estado explícito com múltiplos sinalizadores (loading, refreshing, newsLoading) que AsyncValue não modela naturalmente. API moderna do Riverpod. Custo assumido: dívida frente à direção do ecossistema; migração mecânica pendente.
05Freezed + json_serializable Imutabilidade, igualdade estrutural e serialização sem código manual sujeito a divergência silenciosa. Classes escritas à mão. Rejeitada: copyWith e == manuais são fonte recorrente de defeito.
06Dio com interceptador Injeção de token e tratamento de 401 em ponto único; nenhum repositório conhece autenticação. package:http. Rejeitada: exigiria repetir cabeçalhos e verificação de status em cada chamada.
07Guarda de rota assíncrona Decisão sempre baseada no estado real da credencial, inclusive após limpeza pelo interceptador. Sessão em memória com refreshListenable. Custo assumido: uma leitura de I/O por navegação.
08StatefulShellRoute.indexedStack Preserva pilha e rolagem por aba, com URL sincronizada, sem gerência manual de índice. IndexedStack sob rota única. Rejeitada: exigiria sincronizar estado e URL manualmente.
09Base URL por dart-define Um único artefato de código serve todos os ambientes; nenhum segredo de ambiente versionado. Arquivo .env. Rejeitada: adiciona dependência e um arquivo a mais no fluxo de build.
10Separação SecureStorage / SharedPreferences Dados sensíveis sob cifra do sistema; preferências em armazenamento simples, com leitura síncrona após inicialização. Tudo em armazenamento seguro. Rejeitada: sobrecarga desnecessária para preferência de tema.
11Carga paralela na Home Future.wait faz a latência tender ao maior tempo individual, e não à soma das chamadas. Requisições sequenciais. Rejeitada: tempo de carga cresceria linearmente com o tamanho da watchlist.
12Notícias fora do caminho crítico Cotações e gráficos renderizam sem esperar o endpoint mais lento e menos essencial. Carga única aguardando tudo. Rejeitada: a informação principal ficaria refém da secundária.
13Sincronização diferencial da watchlist No máximo duas requisições ao salvar, independentemente do número de alterações. Uma requisição por toque. Rejeitada: tráfego excessivo e estado inconsistente em falha parcial.
14Repositório de chat simulado Permite desenvolver e validar a UI de conversa antes da existência do serviço de IA, atrás do contrato definitivo. Adiar a funcionalidade. Rejeitada: a UI é substancial e não deveria bloquear em dependência externa.
15Erros por exceção, sem Result Menos cerimônia; cada view model traduz a falha no seu catch para uma mensagem de usuário. Either/Result. Custo assumido: as assinaturas não declaram as falhas possíveis.
16Provider colocado junto da implementação Definição próxima do uso; sem arquivo central que acople todos os módulos. Arquivo único de injeção. Rejeitada: ponto de acoplamento global e conflitos frequentes de merge.

17.4 Recomendações para o pipeline de release

  1. Fixar API_BASE em origem HTTPS na configuração do pipeline, jamais dependendo do fallback local.
  2. Habilitar ofuscação: --obfuscate --split-debug-info=build/symbols, arquivando os símbolos para desofuscação de stack traces.
  3. Alterar o application id Android de com.example.* para o domínio da organização.
  4. Executar flutter analyze e flutter test como etapas bloqueantes antes do empacotamento.
  5. Versionar o incremento de version: em pubspec.yaml junto ao artefato gerado.

18.2 Evolução sugerida

Curto prazo — habilitar publicação

  1. Alterar o application id Android e configurar assinatura de release em ambas as plataformas.
  2. Fixar API_BASE HTTPS e habilitar ofuscação no pipeline.
  3. Concluir a externalização de strings para os arquivos .arb.
  4. Integrar relatório de crash.

Médio prazo — completar o produto

  1. Construir a tela de detalhe do ativo, consumindo getFinancials e getDividends já disponíveis.
  2. Substituir MockChatRepository por integração com serviço de IA, mantendo o contrato existente.
  3. Ampliar a cobertura de testes de widget e introduzir integration_test/ para o fluxo principal.
  4. Implementar exclusão de conta, consumindo o endpoint já mapeado.

Longo prazo — escala e resiliência

  1. Migrar de StateNotifier para AsyncNotifier, aproveitando riverpod_generator.
  2. Introduzir paginação na busca de ativos.
  3. Avaliar atualização de cotações em tempo real por WebSocket, substituindo o modelo de pull.
  4. Adotar layout adaptativo para tablet, web e desktop.
  5. Implementar certificate pinning e, quando disponível no backend, rotação de token.
